# 架构设计

| 项目 | 内容 |
| --- | --- |
| 架构风格 | 前后端分离 + 分层单体（Monolith） |
| 部署形态 | 单 jar 单端口（前端构建产物内嵌） |
| 文档版本 | v1.0 |

**分层职责**

| 层 | 职责 | 不允许做的事 |
| --- | --- | --- |
| web | 参数绑定、校验注解、返回信封 | 写业务判断、直接操作 Repository |
| security | 识别"你是谁" | 判断"你能不能" |
| service | 业务规则、事务边界、数据范围 | 处理 HTTP 细节 |
| repo | 数据访问、条件拼装 | 承载业务语义 |

## 3. 关键设计决策（ADR）

### ADR-01 前端产物内嵌进 jar，单端口部署

- **背景**：作业要求"能远程访问"，而远程主机上同时跑 Nginx + 后端会显著增加部署失败概率。
- **决策**：`vite build` 输出到 `src/main/resources/static`，由 Spring Boot 直接托管；前端使用 hash 路由，无需服务端 rewrite。
- **收益**：`java -jar` 一条命令即可完整运行；无跨域、无反向代理配置。
- **代价**：前端改动需重新打包；开发态仍需 Vite dev server（已配 `/api` 代理）。

### ADR-02 审批规则抽成独立组件 `ApprovalPolicy`

- **背景**：规则如果散落在 Controller 与 Service 中，改一次阈值要动三处，且难以单测。
- **决策**：把"能否审批""通过后的下一状态""当前等待谁"抽成无状态组件，阈值由 `AppProperties` 注入。
- **收益**：9 个纯单元测试在 0.1 秒内跑完，改规则不影响其它层。

### ADR-03 用乐观锁而非悲观锁处理审批并发

- **背景**：审批是典型的"读-校验-写"，两人同时打开同一单据的概率低但后果严重。
- **决策**：实体加 `@Version`，提交时校验版本；冲突由异常处理器统一转 `409`。
- **理由**：审批场景读多写少，悲观锁（`SELECT FOR UPDATE`）会长时间占用数据库连接且容易死锁。
- **代价**：冲突时用户需刷新重试——这恰恰是正确体验，而不是静默覆盖。

### ADR-04 用 Specification 组合查询条件

- **背景**：列表有 6 个筛选条件，而 JPQL 里写 `:param is null or ...` 在 Hibernate 6 下类型推断容易出错。
- **决策**：用 `JpaSpecificationExecutor` 按需拼装条件。
- **收益**：条件可选、类型安全、天然防注入；数据范围也作为一种条件叠加。

### ADR-05 认证采用内存令牌（演示取舍）

- **收益**：零外部依赖，`java -jar` 即用。
- **代价**：重启即掉线；无法多实例共享会话。
- **生产替换路径**：`TokenStore` 换成 JWT 签名校验（无状态）或 Redis 存储，接口不变。

### ADR-06 数据范围在查询层过滤，而不是查出来再筛

- **风险场景**：若先 `findAll()` 再在内存过滤，越权数据已经进入应用内存，且分页总数会错。
- **决策**：`dataScope(user)` 作为 Specification 直接进入 SQL 的 `where` 条件。

## 4. 审批请求的处理链路

以"主管审批"为例：

```
1. AuthInterceptor.preHandle
   解析 Authorization → TokenStore 校验 → 查用户 → UserContext.set(user)

2. PurchaseController.approve(id, body, delayHeader)
   仅做参数绑定，不写业务判断

3. PurchaseService.approve()  [@Transactional]
   a. load(id)                         读实体，拿到 version = V
   b. assertCanView(me, entity)        数据范围校验
   c. policy.canApprove(me, entity)    规则校验（角色/部门/自审）
   d. policy.nextAfterApprove(entity)  计算下一状态
   e. saveAndFlush(entity)             UPDATE ... WHERE id=? AND version=V
        ├─ 影响 1 行 → version=V+1，成功
        └─ 影响 0 行 → 抛乐观锁异常
   f. record(APPROVE)                  写审计流水

4. GlobalExceptionHandler
   OptimisticLockingFailureException → 409 "该申请单正在被其他人处理，请刷新后重试"
```

## 5. 权限模型

三层，逐层收窄：

| 层 | 问题 | 实现 | 失败响应 |
| --- | --- | --- | --- |
| 认证 | 你是谁 | `AuthInterceptor` + `TokenStore` | 401 |
| 功能授权 | 这个动作你能不能做 | `ApprovalPolicy` / Service 内角色判断 | 403 |
| 数据范围 | 这条数据你能不能看 | `dataScope()` 进入 SQL | 403（详情）/ 不可见（列表） |

> 关键原则：**前端隐藏按钮只是体验优化，不是安全措施**。测试用例刻意绕过前端直接调用接口验证 403。

## 6. 前端设计

- **路由**：`/login` 与 `/workbench`，全局守卫检查令牌；hash 模式避免服务端配置。
- **状态**：不引入 Pinia。`session`（登录态）与 `toast`（提示）两个 `reactive` 模块足够，减少依赖面。
- **请求**：`api.js` 统一注入令牌、解析信封、401 自动登出、错误抛出 `status/code` 供调用方区分处理。
- **组件**：
  - `WorkbenchView` 列表 + 统计 + 筛选（容器组件）
  - `RequestDrawer` 详情与审批操作（受控组件，通过 `canApprove/canReject/...` 渲染按钮）
  - `RequestForm` 新建/编辑弹窗
  - `StatusTag` 状态标签

## 7. 扩展点

| 需求 | 扩展方式 |
| --- | --- |
| 多级审批链 | `ApprovalPolicy.nextAfterApprove` 改为查审批链配置表 |
| 预算扣减 | 在 `approve` 事务内调用预算服务，失败则抛异常回滚 |
| 消息通知 | 在 `record()` 后发领域事件，异步消费者发送 |
| 附件 | 新增 `attachment` 表 + 对象存储，单据关联 ID |
| 数据导出 | 新增只读接口，复用 `dataScope` 生成查询条件 |
| 多实例部署 | `TokenStore` → Redis；H2 → MySQL；会话与数据均外置 |

## 8. 已知限制

诚实记录，避免答辩时被问倒：

1. 口令明文存储（演示数据），生产必须 BCrypt/Argon2。
2. 令牌存内存，重启失效、不支持多实例。
3. 工作台统计为内存聚合，数据量上万后应下推 SQL 或走统计表。
4. 无操作频率限制，未做防重放。
5. 无附件、无通知、无导出（见 Spec 第 8 节）。
6. 演示模式开关 `app.demo-mode` 允许请求头延迟，**生产必须置为 false**。
