## 3. 代码审查要点与结论

### 3.1 权限（最高风险区）

| 检查点 | 核查代码 | 结论 |
| --- | --- | --- |
| 未登录能否访问 | `AuthInterceptor` 拦截 `/api/**`（除登录） | ✅ 401 |
| 前端隐藏按钮是否等于安全 | 用例绕过前端直接 POST 审批接口 | ✅ 服务端仍 403 |
| 跨部门主管能否审批 | `ApprovalPolicy.canApprove` 校验 `department` 相等 | ✅ 403 |
| 能否自审自批 | 同上，校验 `applicantUsername != user.username` | ✅ 403 |
| 财务能否看员工草稿 | `assertCanView` 中 `FINANCE && status != DRAFT` | ✅ 403 |
| 列表越权 | `dataScope()` 进入 SQL `where`，非内存过滤 | ✅ 分页总数也正确 |

**审查摘录**

```java
// ApprovalPolicy.java —— 三条约束缺一不可
if (request.getStatus() == RequestStatus.PENDING_MANAGER) {
    return user.getRole() == Role.MANAGER
            && request.getDepartment().equals(user.getDepartment())
            && !request.getApplicantUsername().equals(user.getUsername());
}
```

## 4. AI 生成代码专项审查

本次实践采用"AI 生成 + 人工审查"的模式。人工复审不逐行重写，而是**盯住 AI 最容易出错、且出错的代价最高**的 8 个点：

| # | 高风险点 | 典型错误形态 | 本次核查方式 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | 边界比较符 | `<` 与 `<=` 混淆，5000 元被漏掉财务 | 专门写 4999.99 / 5000.00 / 5000.01 三档单测 | 通过（`compareTo >= 0`） |
| 2 | 只在前端做权限 | 后端接口不校验，改请求即越权 | 绕过前端直接调接口 | 通过（403） |
| 3 | 数据范围做成过滤器 | 先 `findAll()` 再内存筛选，分页总数泄露 | 检查是否进入 SQL `where` | 通过 |
| 4 | 并发下重复写入 | 无版本号，两人同时审批产生两条流水 | 双线程用例 + 流水计数断言 | 通过 |
| 5 | 状态机漏判 | 终态仍可再次变更 | 终态重复审批用例 | 通过（409） |
| 6 | 金额用浮点 | `double` 累加出现精度误差 | 代码走查 + 字段类型 | 通过（`BigDecimal`） |
| 7 | 归属字段信任前端 | 请求体传 `department` 即可伪造 | 检查赋值来源 | 通过（取登录态） |
| 8 | 异常一律 500 | 前端无法区分"该重登"还是"该刷新" | 走查异常处理器分支 | 通过（5 类状态码） |

> 结论：AI 生成的是"骨架"和"常见写法"，**业务规则的正确性必须靠人定义、靠测试固定**。上述 8 点若不做针对性核查，代码能跑通、演示也正常，但会在生产环境出事。
