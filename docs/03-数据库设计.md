# 数据库设计

| 项目 | 内容 |
| --- | --- |
| 数据库 | H2（内存，`MODE=MySQL`）／生产可切 MySQL 8 |
| 表数量 | 3 张业务表 |
| 建模方式 | JPA 实体自动建表（演示）；生产建议 Flyway 管理迁移 |
| 文档版本 | v1.0 |

---

## 1. ER 图

```
┌──────────────────┐
│    app_user      │
├──────────────────┤
│ PK id            │
│ UK username      │
│    display_name  │
│    department    │
│    role          │
│    password      │
└────────┬─────────┘
         │ 1
         │
         │ 由 username 逻辑关联（不建物理外键，便于分库与解耦）
         │
         │ N
┌────────▼─────────────┐          ┌──────────────────────┐
│  purchase_request    │ 1      N │   approval_record    │
├──────────────────────┤◄─────────├──────────────────────┤
│ PK id                │          │ PK id                │
│ UK code              │          │    request_id  (FK)  │
│    title             │          │    action            │
│    reason            │          │    from_status       │
│    category          │          │    to_status         │
│    amount            │          │    operator_username │
│    department        │          │    operator_name     │
│    applicant_username│          │    operator_role     │
│    applicant_name    │          │    comment           │
│    status            │          │    created_at        │
│    version           │          └──────────────────────┘
│    created_at        │
│    updated_at        │
└──────────────────────┘
```

**关系说明**

- `purchase_request` 与 `approval_record` 是 **1 : N**，审批流水只增不改。
- `app_user` 与 `purchase_request` 通过 `applicant_username` 逻辑关联；不在数据库层建外键，原因：
  1. 用户表未来可能拆分到统一权限中心；
  2. 单据需要长期保留，用户离职删号不应影响历史单据；
  3. 申请人姓名在单据上冗余一份（`applicant_name`），保证历史快照可读。

## 2. 表结构

### 2.1 app_user（用户）

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK, AUTO_INCREMENT | 主键 |
| username | VARCHAR(32) | NOT NULL, UNIQUE | 登录名 |
| display_name | VARCHAR(32) | NOT NULL | 姓名 |
| department | VARCHAR(32) | NOT NULL | 部门，数据范围的判定依据 |
| role | VARCHAR(16) | NOT NULL | EMPLOYEE / MANAGER / FINANCE / ADMIN |
| password | VARCHAR(64) | NOT NULL | 演示为明文；生产须 BCrypt |

### 2.2 purchase_request（采购申请单）

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK, AUTO_INCREMENT | 主键 |
| code | VARCHAR(32) | NOT NULL, UNIQUE | 单号 `PR20261022-0001` |
| title | VARCHAR(120) | NOT NULL | 标题 |
| reason | VARCHAR(500) | NOT NULL | 申请事由 |
| category | VARCHAR(20) | NOT NULL | OFFICE / IT_ASSET / TRAVEL / SERVICE |
| amount | DECIMAL(14,2) | NOT NULL | 金额，两位小数，**分级判断依据** |
| department | VARCHAR(32) | NOT NULL | 归属部门（取自申请人，不接受前端传入） |
| applicant_username | VARCHAR(32) | NOT NULL | 申请人登录名 |
| applicant_name | VARCHAR(32) | NOT NULL | 申请人姓名快照 |
| status | VARCHAR(24) | NOT NULL | 见状态字典 |
| version | BIGINT | NOT NULL | **乐观锁版本号** |
| created_at | TIMESTAMP | NOT NULL | 创建时间 |
| updated_at | TIMESTAMP | NOT NULL | 最后更新时间，用于"本月已通过金额" |

> `amount` 使用 `DECIMAL(14,2)` 而不是 `DOUBLE`：金额计算不能有二进制浮点误差，这是财务系统的硬要求。

### 2.3 approval_record（审批流水）

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK, AUTO_INCREMENT | 主键 |
| request_id | BIGINT | NOT NULL, INDEX | 关联申请单 |
| action | VARCHAR(16) | NOT NULL | CREATE / UPDATE / SUBMIT / APPROVE / REJECT / CANCEL |
| from_status | VARCHAR(24) | NULL | 变更前状态（创建时为空） |
| to_status | VARCHAR(24) | NOT NULL | 变更后状态 |
| operator_username | VARCHAR(32) | NOT NULL | 操作人登录名 |
| operator_name | VARCHAR(32) | NOT NULL | 操作人姓名快照 |
| operator_role | VARCHAR(16) | NOT NULL | 操作人角色快照 |
| comment | VARCHAR(300) | NULL | 审批意见 / 驳回原因 |
| created_at | TIMESTAMP | NOT NULL | 操作时间 |

> 审计表不设 `updated_at`、不设删除接口：**只能追加**。这是可追溯性的前提。

## 3. 索引设计

| 索引 | 字段 | 支撑的查询 |
| --- | --- | --- |
| PRIMARY | id | 主键 |
| uk_user_username | username (UNIQUE) | 登录 |
| uk_request_code | code (UNIQUE) | 单号唯一性 + 搜索 |
| idx_request_status | status | 待办、状态筛选、统计 |
| idx_request_dept_status | department, status | 主管的"本部门待审批" |
| idx_request_applicant | applicant_username | 员工的"我的申请" |
| idx_record_request | request_id | 详情页时间线 |

建议在数据量增长后补充：

```sql
-- 覆盖"本部门 + 待主管审批 + 排除本人"这一最热查询
CREATE INDEX idx_req_dept_status_applicant
    ON purchase_request (department, status, applicant_username);

-- 时间范围统计（本月已通过金额）
CREATE INDEX idx_req_status_updated
    ON purchase_request (status, updated_at);
```

## 5. 生产环境 DDL 参考（MySQL 8）

```sql
CREATE TABLE app_user (
    id            BIGINT       NOT NULL AUTO_INCREMENT,
    username      VARCHAR(32)  NOT NULL,
    display_name  VARCHAR(32)  NOT NULL,
    department    VARCHAR(32)  NOT NULL,
    role          VARCHAR(16)  NOT NULL,
    password      VARCHAR(64)  NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_user_username (username)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

CREATE TABLE purchase_request (
    id                 BIGINT        NOT NULL AUTO_INCREMENT,
    code               VARCHAR(32)   NOT NULL,
    title              VARCHAR(120)  NOT NULL,
    reason             VARCHAR(500)  NOT NULL,
    category           VARCHAR(20)   NOT NULL,
    amount             DECIMAL(14,2) NOT NULL,
    department         VARCHAR(32)   NOT NULL,
    applicant_username VARCHAR(32)   NOT NULL,
    applicant_name     VARCHAR(32)   NOT NULL,
    status             VARCHAR(24)   NOT NULL,
    version            BIGINT        NOT NULL DEFAULT 0,
    created_at         TIMESTAMP(6)  NOT NULL,
    updated_at         TIMESTAMP(6)  NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_request_code (code),
    KEY idx_request_status (status),
    KEY idx_request_dept_status (department, status),
    KEY idx_request_applicant (applicant_username)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

CREATE TABLE approval_record (
    id                BIGINT       NOT NULL AUTO_INCREMENT,
    request_id        BIGINT       NOT NULL,
    action            VARCHAR(16)  NOT NULL,
    from_status       VARCHAR(24)  NULL,
    to_status         VARCHAR(24)  NOT NULL,
    operator_username VARCHAR(32)  NOT NULL,
    operator_name     VARCHAR(32)  NOT NULL,
    operator_role     VARCHAR(16)  NOT NULL,
    comment           VARCHAR(300) NULL,
    created_at        TIMESTAMP(6) NOT NULL,
    PRIMARY KEY (id),
    KEY idx_record_request (request_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

## 6. 典型查询

**主管的待办**（对应 `todoScope`）

```sql
SELECT * FROM purchase_request
WHERE status = 'PENDING_MANAGER'
  AND department = '研发部'
  AND applicant_username <> 'lijing'
ORDER BY id DESC;
```

**员工可见范围**（对应 `dataScope`）

```sql
SELECT * FROM purchase_request
WHERE applicant_username = 'zhangwei';
```

**财务可见范围**

```sql
SELECT * FROM purchase_request
WHERE status <> 'DRAFT';
```

> 这三条 SQL 就是"数据范围"的物理落地。任何新增查询都必须先套上这三类条件之一，否则就是越权。

## 7. 数据初始化

`SeedData` 在启动时写入 6 个账号与 9 张覆盖全部状态、跨部门、跨金额档位的单据，同时补齐对应的审批流水时间线。目的是**任何角色登录后都有可演示的数据**，不依赖手工造数。
