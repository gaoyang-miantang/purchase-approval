# AI 协作记录

> 本文记录本项目在使用 AI 辅助开发过程中的**关键提示词、迭代过程与人工介入点**，作为实践的佐证材料。
> 记录原则：只写真实发生的，包括走过的弯路。

---

## 1. 协作模式

```
人（定义与判断）                      AI（生成与提速）
├─ 定义业务规则（谁审、多少钱、能否自审）   ├─ 生成规格文档骨架
├─ 拆分功能与验收标准                    ├─ 生成实体、仓储、控制器
├─ 设计权限模型与状态机                  ├─ 生成前端页面与组件
├─ 判断"这样写会不会出事"                ├─ 生成测试用例
└─ 审查、质疑、修正                      └─ 排查报错、给修复方案
```

**一句话总结：AI 负责"写出来"，人负责"定义对"和"判断会不会出事"。**

## 2. 分阶段关键提示词

### 阶段 1｜需求澄清（不写代码）

> 我要做一个企业采购审批系统，技术栈 Spring Boot 3 + Vue 3。
> 先不要写代码。请帮我梳理：角色有员工、部门主管、财务、管理员四种；
> 金额 5000 以上需要财务复核。请输出功能清单、每个角色的权限边界，
> 并指出这个需求里**最容易被忽略的 5 个边界问题**。

**人工判断**：AI 列出的边界里，"金额正好 5000 怎么办""主管能不能审自己的单""财务能不能看别人的草稿"三条被采纳并写进规格；其余（如跨币种、汇率）判定为超范围，明确写入 Out of Scope。

**产出**：《01-功能规格说明书》第 3、7 节。

### 阶段 2｜状态机与数据模型

> 基于上面的规则，设计申请单的状态机，要求：状态集合完整、每个状态可达、
> 终态不再出边。然后用 ER 图描述数据库，说明金额字段为什么不能用 double。

**人工判断**：AI 初稿给的是 `DRAFT→PENDING→APPROVED` 三态，过于粗糙。要求按"待主管/待财务"拆分后，才有了能支撑两条审批链的状态机。

**产出**：《03-数据库设计》ER 图与三张表结构。

### 阶段 3｜接口契约先行

> 先定 API 契约，不要写实现。要求：统一响应信封、区分 400/401/403/404/409、
> 列表接口支持 tab 与筛选。特别注意：权限不能只靠前端隐藏按钮。

**人工判断**：这一条直接决定了后面的测试可写性——因为错误码语义清晰，才能写出"越权返回 403""并发返回 409"的断言。

**产出**：《04-API接口设计》12 个接口。

### 阶段 4｜核心实现

> 按分层实现：Controller 只做参数绑定，业务规则抽到 ApprovalPolicy 组件，
> 阈值从配置读取。审批用实体 @Version 实现乐观锁，冲突由全局异常处理器转 409。
> 数据范围过滤必须进入 SQL 的 where 条件，不能查出来再在内存筛。

**人工判断**：明确写了"不能内存筛"，是因为这是最容易偷懒、也最容易造成越权的写法。

**产出**：`ApprovalPolicy`、`PurchaseService`、`AuthInterceptor` 等 27 个类。

### 阶段 5｜测试

> 为审批规则写单元测试，必须覆盖：4999.99 / 5000.00 / 5000.01 三档、
> 跨部门主管、自审自批、财务节点错位。再写一个并发测试：
> 两个线程同时审批同一张单，断言只有一个成功、审批流水只有一条。

**人工判断**：并发用例的断言不能只写"有一个失败"，必须断言**失败原因是乐观锁**，否则并发可能根本没打到数据库层，测试会假通过。

**产出**：19 个 JUnit 用例。

### 阶段 6｜审查

> 以代码审查者身份，列出这类审批系统最容易出的 8 类问题，
> 每类给出"错误形态 + 如何验证"。不要泛泛而谈，要能落到具体断言上。

**产出**：《05-审查报告》第 4 节"AI 生成代码专项审查"。

### 阶段 7｜界面

> 工作台要有统计卡片、待我审批/全部/我的三个视图、详情抽屉含审批时间线。
> 不要引入 UI 组件库，自己写样式，保证构建产物尽量小。

**人工判断**：不引 UI 库是工程决策（见下方 BUG-02），不是审美偏好。

## 3. 迭代过程记录

### 3.1 产品层面的关键迭代

| 轮次 | 变化 | 触发原因 |
| --- | --- | --- |
| v0.1 | 三态状态机（草稿/待审/完成） | 初稿，无法表达两级审批 |
| v0.2 | 拆为六态，主管与财务分离 | 金额分级需要两个节点 |
| v0.3 | 增加"自审自批"禁止规则 | 评审发现：主管给自己批单是内控漏洞 |
| v0.4 | 财务可见范围从"全部"收窄为"非草稿" | 评审发现：草稿属申请人隐私 |
| v0.5 | 增加乐观锁与 409 语义 | 评审发现：并发会重复审批 |
| v1.0 | 前端组件自研，去掉 UI 库 | 构建环境不兼容（见 3.2） |

### 3.2 工程层面的问题与处置

| # | 问题 | 定位方式 | 处置 |
| --- | --- | --- | --- |
| 1 | 机器上没有 JDK / Maven | `java -version` 报命令不存在 | 下载便携 JDK 17 + Maven 到项目外目录，走国内镜像，不动系统环境 |
| 2 | 前端依赖装不上：pnpm 隔离模式下路径超 260 字符 | 删除 `node_modules` 时大量"路径的一部分找不到" | 改 hoisted 布局；仍不稳定后改用 npm |
| 3 | 引入 Element Plus 后依赖树过深 | 同上，且安装体积大 | **去掉 UI 库**，自研 6 个组件，依赖 54 → 33 个 |
| 4 | Vite 构建报 `spawn EPERM` | esbuild 需要以管道启动子进程 | 确认沙箱限制后放宽一次权限完成构建 |
| 5 | 编译报"构造器不可见" | javac 明确指向 `PurchaseRequest()` | `protected` 改 `public` |
| 6 | 集成测试全红：Mockito 无法加载 MockMaker | 堆栈指向 `mockmaker` 自附加失败 | 加 `mockito-extensions` 配置切换为 subclass mock maker |
| 7 | `mvn package` 报无法重命名 jar | 运行中的进程占着 jar | 先停服务再打包，并写进操作手册 |
| 8 | 截图需要浏览器，但进程间通信被拒 | Chrome 报 `platform_channel.cc 拒绝访问` | 确认是命名管道限制后放宽权限启动，用 CDP 抓图 |
| 9 | 审批抽屉"驳回"是红色实心按钮 | 截图走查 | 主次调整：通过=主按钮，驳回=红色描边 |

> 第 2、3、4、6、8 条都不是"代码写错"，而是**环境与工具链的坑**。这类问题的处理经验，往往比写出业务代码更花时间。

### 3.3 人工介入的关键节点

以下判断 AI 给不出，必须由人拍板：

1. **"金额正好 5000"归谁** —— 业务口径问题，没有标准答案，必须定义清楚并写进测试。
2. **管理员能不能审批** —— 决定"系统管理员"与"业务审批人"的职责边界，本项目选择**不能**。
3. **并发冲突给用户什么反馈** —— 选择"明确报错让用户刷新"，而不是"静默覆盖"。
4. **哪些功能明确不做** —— 主动划边界，避免做成半成品。
5. **演示开关是否允许存在** —— 允许，但必须默认关闭并在文档中标红。

## 4. 提示词经验

### 4.1 有效与无效的对比

| 类型 | 差的写法 | 好的写法 | 差异 |
| --- | --- | --- | --- |
| 定义 | "写一个审批系统" | "四种角色，金额 ≥5000 走财务，主管只能审本部门且不能审自己的单" | 后者可直接落成测试用例 |
| 约束 | "注意安全" | "权限判断必须在服务层，前端隐藏按钮不算；越权返回 403" | 前者无法验收 |
| 边界 | "处理一下边界" | "列出这个需求里最容易被忽略的 5 个边界问题" | 把"想边界"这件事显式化 |
| 验证 | "测试一下" | "断言失败原因必须是乐观锁异常，而不是任意异常" | 防止测试假通过 |
| 顺序 | "把系统写出来" | "先定 API 契约，不要写实现" | 契约先行，测试才写得出来 |

### 4.2 三条体会

1. **先定义，再生成**。规则没定清楚就让 AI 写代码，产出一定是"看起来对但经不起问"的。
2. **把验收标准写进提示词**。"返回 409"比"处理好并发"有用一百倍。
3. **AI 的产出必须能被验证**。能被测试固定的才算实现，不能被验证的只是"像那么回事"。

## 6. 复盘

**做得好的**：

- 契约先行（先定 API 再写实现），让测试可以脱离界面独立验证。
- 把规则抽成 `ApprovalPolicy`，9 个单测 0.1 秒跑完，改规则心里有底。
- 每一条"高风险点"都配了可执行断言，而不是靠人眼确认。

**可以更好的**：

- 前端组件自研花了额外时间，若环境允许，UI 库能省一半时间。
- 编辑草稿、作废两个功能缺独立集成用例，目前靠黑盒脚本覆盖。
- 没有做前端单元测试。

**如果重来**：会先花 30 分钟把环境和工具链跑通（JDK、Node、构建链路），再开始写业务代码——本次有近一半的返工来自环境，而不是业务。
